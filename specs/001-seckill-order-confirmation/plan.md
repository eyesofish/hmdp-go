# 实施计划 · 秒杀订单确认与订单号展示

依据[功能规格](spec.md)。V3 秒杀请求在 Redis 预扣成功后即可返回订单号，Kafka 投递失败且订单进入补投队列时也会返回。商铺详情页现在一收到这个响应就显示成功。消费者随后在同一笔 MySQL 事务里扣减券库存并创建订单，**事务提交**才是页面可以确认成功的依据。

## 前后端接口约定

以下路径为 Go 路由；浏览器通过 Nginx 的 `/api` 前缀访问。两个路由均使用现有登录中间件。

| 请求 | 响应示例 | 页面行为 |
| --- | --- | --- |
| `POST /voucher-order/seckill/10`，受理成功 | `{"success":true,"data":"661639913812262913"}` | 保存字符串 ID，显示“订单处理中，请勿重复提交”，开始查询。 |
| `GET /voucher-order/661639913812262913/confirmation`，尚无本人的已提交记录 | `{"success":true,"data":{"confirmed":false}}` | 保持处理中，继续查询。 |
| 同一 GET，已查到本人的订单 | `{"success":true,"data":{"confirmed":true,"orderId":"661639913812262913"}}` | 核对与受理 ID 一致，显示“抢购成功”和完整号码。 |

- 在 HTTP 边界将订单 ID 格式化为十进制字符串。现有服务层测试、Kafka 消息和数据库继续使用整数。POST 的 JSON 类型从数字改为字符串，前后端在同一个 PR 交付；外部调用方若按数字解码也需要适配。
- GET 从登录上下文读取用户 ID，校验路径参数为正的有符号 64 位十进制订单号，使用参数化查询 `SELECT id FROM tb_voucher_order WHERE id = ? AND user_id = ?`。仅查到记录时确认。其他用户的订单与不存在的订单均返回 `confirmed:false`，其含义仅为“当前用户尚无可确认的订单”。格式非法返回 400，未登录沿用 401，数据库错误返回 5xx。确认响应使用 `Cache-Control: no-store`，防止缓存未确认状态。
- Kafka 已接收消息、Redis 待投递记录已删除，都可能发生在 MySQL 提交之前。确认接口只读已提交的订单记录。

## 商铺详情页

- 以券 ID 记录页面状态。点击时立即禁用该券按钮并在事件处理器防重入；POST 明确拒绝时展示现有错误提示。已受理时在券卡上持续显示处理提示。
- 收到受理 ID 后立即查询；每次待确认响应结束后等 1 秒再查，每张券最多一个在途查询。暂时的查询网络错误或 5xx 保留处理状态并重试。成功后停止查询并保持该券不可重复提交。离开页面时停止定时器，忽略迟到的响应。页面全程按字符串传递和展示订单号。

## 浏览器测试与 CI

1. 使用 Playwright Test 和 Chromium。通过独立 Compose 项目启动 MySQL、Redis、Kafka、Go API 和 Nginx。测试专用 Compose 覆盖文件将 API 配置指向容器服务名、Kafka 内部监听地址，将 Nginx 上游指向 API 容器。使用独立卷和端口，避免连接开发库。初始化全新测试用户和有库存、处于有效期的券，通过真实登录会话打开详情页。独立 Redis 的首笔订单序列号为 1；从数据库取得文本 ID 后验证其经 JavaScript Number 转换会失真，确保用例确实覆盖精度风险。
2. 浏览器点击前，用独立 MySQL 连接开启事务，对测试券执行 `SELECT voucher_id FROM tb_seckill_voucher WHERE voucher_id = ? FOR UPDATE`。消费者会在扣该券库存时等待，API 仍能受理和查询。全程用另一条自动提交的连接读取订单，避免事务快照影响断言。
3. 点击前开始记录页面可见成功提示和下单请求数。持锁时应能观察到受理、按钮禁用、至少一次未确认响应、库内零条对应订单，且从未显示成功。尝试再次操作该券后仍只有一次 POST。用例先在旧版本运行并记录提前显示成功的红灯。
4. 释放行锁，从释放时刻起最多等 10 秒，按用户 ID 和券 ID 独立查询 `tb_voucher_order`，应恰有一条记录。用 `CAST(id AS CHAR)` 读取完整号码，与页面成功提示中的数字逐字符比对。失败报告包含用户、券、观察到的提示和 SQL 结果；保留脱敏诊断信息。锁连接在测试清理阶段始终释放。
5. 本地和 PR 的独立 `e2e` job 使用同一入口 `npm --prefix tests/e2e test`；用例随附锁文件及安装 Chromium 的命令。入口负责启动环境、等待 API 就绪、运行用例和清理本次环境。CI 另行执行仓库已有的 Go 检查。前端资源、Compose 配置及测试依赖须包含在 PR 内，使干净检出也能运行。
